# Your own patterns: the build log

This is the working log for building the plan at `#/plan` (written in `apps/player/src/review/Plan.tsx`): learners make their own patterns, by saving their own inking and colours, by copying a tutorial at any step, from nothing, and from building blocks. The owner approved the plan and its order on 6 October 2026 and asked for it to be built by two agents, a builder and a tester who uses the app like a person and reports what goes wrong.

**If work stopped (a usage limit, a crash), resume here:** take the first unticked task below, read its notes and the latest tester report at the bottom, and carry on. Every finished task is ticked, committed with its number in the message, and pushed.

## The owner's decisions (6 October 2026)

The phases go in the order below. Every user pattern is a true ruler and compass construction: the editor only lets you click points that exist, and there is no free drawing. Patterns are kept in the browser first, then as a file and a share link; accounts come later, with a server. Good user patterns may join the library after review on the review page, with a golden test and the maker named in the credits. We use the editor ourselves to make library tutorials.

## How the two agents work

The builder takes one task at a time, shows nothing to the owner until it works, runs `pnpm test`, `pnpm lint` and `pnpm typecheck`, commits with the task number (“User patterns 1.2: …”), pushes, ticks the task here and adds anything learned to the lessons at the bottom. The builder never runs `pnpm format` over the whole repo (it rewrites the tool JSON in `tools/review/`); it runs Prettier on the files it changed.

The tester starts its own dev server on a spare port (never the owner's on 4200), drives the app in headless Chromium with `playwright-core` from `~/.cache/tastir-tester/` (the browser is `~/.cache/ms-playwright/chromium-1243/chrome-linux64/chrome`), and goes through each finished phase the way a learner would, from the home page, by clicking. It writes a dated report at the bottom of this file: what it tried, what worked, what was confusing or broken, with screenshots saved under `docs/review/user-patterns/` (ignored by git). The builder fixes what the report finds before moving on.

## Lessons

- `pnpm format` rewrites the JSON in `tools/review/` (thousands of lines of line breaks), which then looks like real changes; run Prettier only on the files you changed. (6 October)
- The player steps on Space and the arrow keys from a window listener, so any text box in the player must be skipped there, or typing a design's name steps the tutorial. (6 October)
- A design's wall needs its inked pattern, which is slow for big tutorials, so the worker makes it: `useModel(json, inked)` sends the pieces with the tutorial and the worker applies `withInking` (model.ts) before replying. The player itself still re-inks on the main thread, as free inking always did. (6 October)
- A pick rule must be checked against the crossings the engine sees, so `pickFor` (engine `picking.ts`) only proposes rules and then evaluates each with `crossingOf`, the same code a point step runs; `angle: 90` can pick a crossing at 45° when the other is at 225°, so the crossing's own round angle is tried first. (6 October)
- jsdom has no CSS, so two copies of a control hidden by media queries both show in tests and break `getByRole`; choose the one place by screen width in code (`useNarrow` in app.tsx) instead. (6 October)
- The engine stops at the first step it cannot evaluate, so the editor's `check` (editor/document.ts) sets that step aside with its reason and evaluates again until every step works or is marked broken; `evaluate` reads only the steps, so a draft with no ink or tile evaluates. Designs and patterns share one safe localStorage list (`app/storage.ts`). (6 October)
- Check every layout change at 1280, 1100, 1024, 900, 800 and 390 px: between 761 and 1100 px the player had a fixed screen height, so the colour panel, placed under the wall, was squeezed onto the wall (found by the tester, and older than phase 1). To compare with an old commit, use `git worktree add` in the scratch folder with symlinks to `node_modules` and `apps/player/node_modules`, and run its Vite on another port. (7 October)
- The editor snaps only near the click: it takes the elements within reach and crosses just those pairs, then asks `pickFor` for the rule, so it never lists every crossing of a big drawing. For jsdom tests, give the drawing a `getBoundingClientRect` and click at screen positions worked out from its `viewBox`. (7 October)
- The editor offers only the bits of line a file can name: each must run along a line or polygon side of the construction and end where an element crosses it. Bits drawn only by a neighbouring tile's copy are left out, because ink written outside the tile is repeated only one tile either way (computePattern) and would leave gaps. A user pattern plays at `#/mine/<id>`; the player gets an `address` so its designs and copies point back there. (7 October)
- Never leave half-done work in the main tree for long: the tester's dev server picked up unfinished editor code live and two polygon steps vanished in its run. The tester now tests from a frozen worktree of the last commit, which is the right way; the builder commits each task as soon as it passes. (7 October)
- Saving a pattern again keeps its piece names: `tutorialOf` computes the pieces with the draft's earlier expect block, so matching pieces keep their names, colours and placements, and only new ones get plain names. Every library tutorial round-trips through the editor and passes the golden checks (roundtrip.spec.ts, two seconds for all 34). (7 October)
- Never let a learner read an internal name (c, d1, S1): step texts and engine reasons go through `describe` and `plainReason` (editor/document.ts), which name lines, circles and shapes by how they were made; points keep their names, since the drawing labels them. (7 October)

## Tester reports

### Phase 1, tester report (6 October 2026)

I went through phase 1 as a learner, by clicking from the home page at 1280x800 and on a phone (390x844), with my own server on port 4351. On the eight-fold star and cross I used “Make your own” to ink the inner square, which turned the star into a square and four triangles, recoloured the pieces, saved the design as “Pointy star” and reloaded. On the Comares bath stars I re-inked a few lines and saved from the ink stage, then recoloured and pressed Save. On the Bou Inania rosette I recoloured and changed the wall style before saving. I then opened each design from the shelf, used Save and Save as new, renamed designs and deleted them. I also tried an empty name, a 300-character name, Escape, a design address that does not exist, a corrupt and a half-corrupt `tastir.designs`, storage whose `setItem` throws, storage that is really full, a page where reading localStorage throws, and designs whose inked lines no longer exist. Screenshots are in `docs/review/user-patterns/phase1/`.

Most of it works well, and I could not make the app crash. The save form sits in the page, starts with the tutorial's name selected and saves on Enter, and typing spaces in it does not step the tutorial. After saving, the address becomes `#/<tutorial>/design/<id>` and a clear line says where the design went (18). The shelf shows each design as its own wall, with my inking and colours drawn correctly for all three tutorials (19c, 36, 39), and the designs survive a reload. Opening a design lands on the wall with the right pieces, colours, palette and wall style, and the ink stage shows my inking (20, 21, 37, 40). From the shelf, the Comares design opened in about 0.2 s and the Bou Inania design in about 0.9 s. On the shelf, the Bou Inania wall took about 2.7 s to draw, with a striped placeholder and “Checking the tutorial…” in the meantime (35). Save updates the design in place and Save as new suggests “Pointy star (2)” and makes a second card. Delete asks inline (“This cannot be undone”, Delete in red, Keep it), Keep it keeps the design, and deleting the last design removes the shelf (27). An empty or blank name disables the Rename button. A corrupt or wrong-shaped store reads as no designs, and the good designs in a half-corrupt store still show. When storage cannot be read at all, the home page and the player still work. A stale design opens with the tutorial's own lines, keeps its colours, and explains why in orange (48). The phone layout has no sideways scroll, and the shelf, the opened design and Save as new all work there (56). I saw no console errors or page errors anywhere.

**Real bugs**

1. **Saving fails silently when the browser refuses to store.** To reproduce, block or fill storage (I made `setItem` throw, and in a second run I really filled the localStorage quota), go to the ink stage, press Save as my design, type a name and press Save. I expected a message saying the design could not be kept, for example “This browser would not save it (private window or storage full)”. Instead nothing happens: the form stays open, the address does not change and nothing explains why, so a learner presses Save again and again (45, 50). The app does not crash, which was promised, but a learner in a private window loses their work without knowing it.
2. **Escape does not close the rename box.** To reproduce, press Rename on a shelf card, type something and press Escape. I expected Escape to cancel, as Cancel does. The box stays open with the typed text, and only the Cancel button closes it (24).

**Suggestions**

3. A missing design is shown like a crash. Opening `#/eight-fold-star-and-cross/design/doesnotexist` shows the title “This pattern cannot be shown” and the reason in red monospace text on an empty page (41). The reason itself is good (“Designs are kept only in the browser they were made in”), but the page should look like an ordinary message and offer “Open the tutorial” beside “All patterns”. The same message appears when a real design id is put after the wrong tutorial, where “not saved in this browser” is not true.
4. Names have no length limit. A 303-character name is accepted and wraps to ten lines on the shelf card, which pushes its buttons down and breaks the grid (26). A limit of about 60 characters, or cutting the name to two lines with an ellipsis, would fix it.
5. The My design box is hard to find on big tutorials. At the colour stage it comes after every piece row, which is 14 rows on the Bou Inania rosette, so on a laptop and on a phone you must scroll the side panel to find Save (40, 56). An opened Comares bath design also shows the original photo first, which pushes the box further down (37). Putting My design above the colour list, or keeping the Save buttons in view, would help.
6. Nothing says when there are unsaved changes. After opening a design and recolouring, Save looks the same as before, and leaving through All patterns drops the changes without a word. A small “unsaved changes” note, or Save enabled only when something has changed, would make it clear.
7. A store that does not parse is overwritten on the next save. With a corrupt `tastir.designs`, the next save replaces it with a list holding only the new design. For random garbage this is fine, but if it ever happens because of a future format change, the learner's older designs are wiped silently. Keeping the unreadable value under a backup key before writing would be safer.
8. On a fresh visit the shelf is below the fold at 1280x800, under the hero (19). A returning learner has to scroll to find their designs, so a “My designs” link near the top would help.
9. Not phase 1, but seen while testing: the colour stage shows internal piece names such as “cross_arm”, “small_star”, “outer2” and “shield2” in the piece list and in the step text (34, 40).

### Editor (2.2–2.4), tester report (7 October 2026)

I tried the editor as a hobbyist who wants a pattern of their own. My server ran on port 4351, at 1280x800 and on a phone (390x844). The builder was changing files while I worked, and in the first minutes the page picked up the unfinished 2.5 work (a Construct/Ink switch and a Tile tool appeared, and two polygon steps I had just drawn vanished). So I ran the rest from a frozen copy of commit 26a3503, and nothing below comes from half-finished work. Screenshots are in `docs/review/user-patterns/editor/`.

I opened the star and cross from the home page, went to step 3 and pressed “Make my own copy from here”. The editor opened at `#/edit/<id>` with the three steps, the credit line “Based on Eight-fold star and cross, up to step 3” linking back, and a drawing with named points (02). I then used every tool. Polygon through E, N, W, S and back to E made a square (04). Ruler, Compass, Same opening, Opening from two points, Square to, Parallel, Halve angle, Touching (centre, a line, Done) and Point each made a step that works, and each gave a plain step text such as “Draw L1 through N, square to d1” or “Halve the angle N–O–NE with L3” (10–19, 22). Each tool says on a line under the drawing what to click next, in the order of a real construction, which reads well. I made the plan's Figure 4 with two Polygon steps, an octagon through the eight points and an eight-pointed star through every third point, in about twenty clicks (20). Point marks an unnamed crossing as P1 when the click is within about 7 px of it, and says “There is no point there” on empty paper or 14 px away (21). The title and step texts can be edited and survive a reload. Undo and Redo work with the buttons, Ctrl+Z and Ctrl+Shift+Z, and Undo also takes back a text edit.

Deleting step 2 asks first: “Step 2 is used by steps 3, 4, 5, 6, 7, 8 and 9, which would break without it”, with Delete all 8, Only step 2 and Keep (23). With “Only step 2”, every later step turns red with ✗, the list says “7 steps are broken”, and each broken step explains itself. For example, it says “It uses NE, which step 2 was to make, and step 2 is broken”, which a learner can follow (24, 25). Undo brings everything back. Copying the Bou Inania rosette at its last step took 0.3 s. Adding a Ruler step there took about 1 s, and a reload about 0.9 s, with the new step kept. On the phone, the copy button, the tool bar and Polygon by tapping work, with no sideways scroll (33). I also re-checked 1.5. At 800, 1024 and 1100 px the colour stage now stacks cleanly with nothing on top of the wall (40, 42). The browser's Back button with unsaved changes now asks in a dialog, Leave without saving or Stay (41). I saw no page errors.

**Real bugs**

1. **Nothing leads back to a copy once you leave the editor.** To reproduce, make a copy, add steps, press All patterns, and look for it. I expected a “My patterns” shelf or something on the home page like My designs. There is nothing, so the only way back is the browser history or a saved address. Everything is still kept in the browser (`tastir.patterns`), but a learner cannot reach it. This is the first thing a hobbyist will hit.
2. **The big copy is unreadable.** Copying the Bou Inania rosette draws all 1535 point names at once (P0, Q30, M184, St1a and so on) on top of each other. The drawing becomes a grey mass in which no point can be picked, and a learner cannot see what to click (27). The missing zoom, a gap the builder already lists, makes this much worse, but even with zoom the names need to be hidden unless near the pointer or zoomed in.
3. **Two names on one point, and the step text uses the hidden one.** On the star and cross, A and E sit on the same point and their labels are drawn on top of each other, so it looks like a blurred “E” (02, 20). Clicking it writes “Join A, N, W and S…” in the step text, although the learner thinks they clicked E. Showing one name per point, the one the tutorial uses in its own text, would fix both.
4. **After “Only step N”, the delete question stays open for the next step.** Delete step 2 with Only step 2: the step that moves up into place 2 is selected, and the box “Step 2 is used by steps 3, 4 and 7 … Delete all 4 / Only step 2 / Keep” is already showing, although I did not press Delete again (24). A second click on the same spot deletes a second step.
5. **The drawing moves after the first click of a multi-click tool.** With Polygon (and the other tools that show Done and Cancel), the Done/Cancel row appears under the drawing after the first click. The drawing then shrinks and moves up by about 15 px, so the next click where the point used to be lands on empty paper with “There is no point there” (03-poly-E, 05). Keeping the Done/Cancel space always reserved would stop the jump. Separately, Escape does not cancel a polygon in progress, although Cancel does.

**Suggestions**

6. Internal names leak into what the learner reads. Examples are “Keep the opening of c and draw the circle C1 around NE” (c is the first circle), “d1”, and the broken-step reason `d1: "E" does not exist` with code-style quotes. “The first circle”, “the diagonal” and “E, which step 2 made, is gone” would read better.
7. “What is saved”, the raw JSON of the step, takes half the right-hand panel. A hobbyist will find it intimidating, so it would be better folded away under a “Show the file” toggle.
8. Unnamed crossings are invisible until marked. A learner cannot see that the chord and the diagonal cross somewhere clickable until they try. Drawing small faint dots at crossings near the pointer would show where to click.
9. The Bou Inania copy says “up to step 13” and the player said “Step 13 of 13”, but the copy lists 14 steps (an extra “Mark the corners of the pattern”). The player's step buttons, meanwhile, go up to 23. The numbers do not agree anywhere.
10. On the phone, the step list and both rows of tools come before the drawing, so the drawing starts below the fold, the status line is further down still, and the title is cut (“Eight-fold star ar”). The point names are very small.

The gaps the builder already lists, and how much they hurt:
- **No zoom or pan:** the drawing is fine on small copies, but it makes the big copy unusable (see bug 2), so it hurts a lot there.
- **New steps only at the end:** this did not stop me, because I only built forwards, so it hurts little for now.
- **Touching side cannot be chosen:** I never needed it, so it hurts little.
- **Copy button below long step text on phones:** on the star and cross it was just above the bottom bar and easy to find, so it is a small issue.

My verdict: the editor already works as a true ruler-and-compass editor for small patterns. A hobbyist who copies the star and cross can follow the hints, build Figure 4, see clearly why steps break, and undo. Bugs 1 and 2 must be fixed before learners use it: without a way back to their copy their work feels lost, and big tutorials cannot be edited at all.
